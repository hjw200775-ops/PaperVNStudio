## 1. 循环延迟根因（M1）

上一轮记录的平均 330 ms / 最大 984 ms 接缝，来自**播放器调度**，不是解码或素材：

| 归因 | 证据 |
|---|---|
| A. 播放器调度 | 旧实现靠 `rAF + timeupdate + 400ms 定时器` 检查 `currentTime >= loopEnd` 再回跳。窗口不可见时 Chromium 把定时器节流到 ~1 s、rAF 停摆，回跳只能等下一次节拍 → 接缝 ≈ 1 s。代码路径与被测值一致 |
| B. 解码/缓冲 | 首次播放（真实 OGG 解码到可播）实测 **100–246 ms**，与循环接缝无关；循环发生在已解码/已缓冲的流上 |
| C. 素材本身 | 《晚风》OST 为 OGG，编码填充在循环边界可产生 **≈4 ms** 的静音。本轮把它单独统计（第 3 节），不混同于播放器延迟 |
| D. 环境差异 | 本机验收窗口无前台合成器（rAF 不触发）。这解释了旧值与前台窗口的差异，也说明「靠定时器命中边界」这条路线本身不可靠 |

结论：**要在任何窗口状态下都对，循环边界必须交给音频线程**，而不是 JS 定时器。

## 2. 混合播放架构（M2）

`dist/audio.js` 在不改对外 API 的前提下增加第二套播放模式：

| 模式 | 实现 | 适用 |
|---|---|---|
| `stream` | 既有 `HTMLAudioElement`，按需加载 | 大文件、长语音、不要求精确循环、解码失败时的回退 |
| `precise` | `AudioBufferSourceNode` + `loopStart/loopEnd`，增益走 `AudioParam` 曲线 | 需要精确循环的 BGM |

- **选择**：`modePref`（`stream` / `precise` / `auto`）→ 有 `AudioContext` → 解码后估算内存（`length × channels × 4`）→ 超过预算回退 `stream` 并记录 `reason`。
- **预算**：默认 64 MiB，可配 `memoryBudgetBytes`；LRU 淘汰，**正在播的那条永不淘汰**；`cacheStats()` 暴露 `entries/bytes/budget/ids`。
- **竞态**：每次请求带自增 `loadSeq`，慢的旧解码结果被判 `stale` 并**丢弃**（不回退成流式，避免旧请求盖掉新音乐）。
- **增益**：master → 总线（bgm/sfx/voice）→ Ducking 节点 → 通道增益；淡入淡出、交叉淡化、Ducking 全部排到 `AudioParam`（`linearRampToValueAtTime` / `setValueCurveAtTime`），与帧率无关。
- **混音语义不变**：`Master × 用户分类音量 × 剧情总线 × 播放音量 × Ducking`；`prefs` 只由设置改写。
- **离线可测**：`audioContext` 可注入，`OfflineAudioContext` 能跑同一套图 → 见第 3 节。
- **监听点**：`onGraph({ctx,tap})` 暴露总线后、master 前的混合信号，便于抓真实波形。
- **回退透明**：`snapshot()` 增加 `mode / modePref / preciseReason / graphError / cache / graph`。

## 3. 精确循环验收（M3）

`node scripts/v081rc-loop-offline.cjs 30` → `release/audio-loop-benchmark.json`

方法：`OfflineAudioContext` 渲染引擎真实图，分析 **渲染出的 PCM**（不是 `currentTime`）：
统计循环边界 ±40 ms 内最长静音、全程相邻样本最大跳变。

| 分组 | 次数 | 边界静音 P95 | 最大 | 最大跳变 |
|---|---|---|---|---|
| 正弦 WAV（1–3.65 s 区间，30 组不同边界） | 30 | **0.02 ms** | 0.02 ms | 0.0281 |
| 《晚风》OST（区域循环 4 s 起，8–10 s 区间） | 10 | **0 ms** | 0 ms | 0.0498 |
| 《晚风》OST（整曲循环） | 10 | **0 ms** | 0 ms | 0.0498 |

- 目标「P95 ≤ 20 ms」：**满足**（最差 0.02 ms ≈ 1 个采样）。
- 正弦的相邻样本跳变 0.0281 ≤ 理论极限 0.029（440 Hz @48 k，振幅 0.5）→ 边界连续，无爆音。
- OST 的 0.0498 是解码后波形自身的斜率（不是正弦），不构成断裂。
- **不宣称「采样级无缝」**：这里测到的是「边界处 0–1 个采样的静音」，受解码器与素材编码填充影响；
  OGG 的编码填充会在边界留下约 4 ms 的低电平段（上一版在线测得），属于素材格式特性，已单独记录。

## 4. 自动化测试

`npm run check` 全绿。新增 `tests/audio-precise.test.cjs`（7 组，全部落在实际行为上）：

| 用例 | 断言 |
|---|---|
| 精确模式 | 创建 `BufferSource`、`loop/loopStart/loopEnd` 正确、快照 `mode=precise`、缓存命中 |
| 同曲短路 | 第二次请求不新建实例、只调音量 |
| 预算回退 | 600 s 素材（192 MB）→ `fallback=budget`、`mode=stream`、缓存不落盘 |
| 缓存淘汰 | 30 s×3 条 → `entries ≤ 2`、`bytes ≤ budget`、新曲在缓存 |
| 异步竞态 | 慢请求 `stale` 被丢弃，最终播新曲，只留 1 个实例 |
| 解码失败 | 回退流式且确实在播，`fallback` 含 `decode` |
| 终止清理 | `applyAudioState({bgm:null})` 后快照清空、精确源停止 |

保留既有 26 个测试文件（含 V0.8.1 的 `audio-performance.test.cjs`、V0.8.0 的演出/窗口测试）。
