## 2. 1 GiB 测试工程

生成脚本：`scripts/make-large-project-m3.cjs`（可复现，素材本体不进 Git）。

| 项目 | 实测 |
| --- | --- |
| 去重后素材总大小 | **1,576,200,076 bytes**（1.47 GiB，≥ 1,073,741,824） |
| 唯一内容哈希 | 204（100 图 + 104 音频，无重复素材） |
| 图片 | 100 张 1600×900 / 1200×1800 随机 RGB PNG，CRC 与 IHDR 抽样校验通过 |
| 音频 | 104 段 60 s、44.1 kHz 立体声 PCM WAV，RIFF/WAVE/data 头校验通过 |
| 剧情 | 12 章 / 72 段 / 576 节点 / 6 角色，背景、立绘、表情、BGM、SFX、Voice 均有真实引用 |
| 运行时工程 JSON | 522,941 bytes（无 Base64）；磁盘 `project.paper.json` 888,831 bytes |

不使用空文件、稀疏文件、重复素材或不可解码文件虚增体积。**过程中曾发现测试 PNG 的 CRC32 表生成写错（`c>>>0` 应为 `c>>>1`），导致图片在浏览器里无法解码；已修正生成脚本、窗口冒烟脚本与单测共 3 处，并用 Python 逐块复核 CRC/IHDR/WAV 头后重新生成工程。**该问题属于测试夹具，不是产品协议缺陷，但如实记录。

## 4. 性能与内存（真实采样）

机器：Windows x64，12th Gen Intel Core i5-12400F（12 逻辑核），32 GiB 内存，Electron 45.3.2 / Node v22.22.2，本机 SSD（F: 盘，验收前可用 216 GiB）。

采样方法：CDP 每 150 ms 调 `app.getAppMetrics()`（主进程 Browser、渲染进程 Tab、`workingSetSize` 由 KB 换算字节），tasklist 每 250 ms 独立采样所有 `electron.exe` 工作集；每个阶段首尾强制各采一次，因此连 30 ms 的导入阶段也有采样点。共 214 点（CDP 114 / OS 100），覆盖 12 个阶段。

| 指标 | 实测峰值 |
| --- | --- |
| 主进程工作集 | **514.8 MB**（539,791,360 bytes） |
| 渲染进程工作集 | **324.5 MB**（340,246,528 bytes） |
| 所有 Electron 进程总工作集 | **1,118 MB**（1,172,299,776 bytes） |
| 单进程 peakWorkingSetSize 最大 | 见 `memory-profile.json` |

耗时（ms）：导入 707、打开 1,401、保存 1,120、重开 3,033、预览启动 3,959、目录版导出 3,960、导出游戏启动 2,288；编辑 762、撤销重做 840、场景切换 1,341、音频 1,026、单文件守卫 829。

界面卡顿：验收脚本在各阶段以 CDP 轮询等待真实 DOM/解码状态，未观察到长时间无响应或需要强制跳过的阶段；**未做逐帧 FPS 采样**，因此不给出"零卡顿"的量化结论。异常事件 0 条。

明确未测量（报告中也标注）：1 GiB 工程单文件 HTML 导出的渲染进程堆峰值（按设计不执行该导出）、第二台机器 / 不同 GPU 基线、GPU 显存占用。没有根据素材体积推算内存，所有数值来自采样。

## 8. 边界（不夸大为已解决）

1. 单文件 HTML 保持 200 MB 上限；1 GiB 工程按设计走目录版 / ZIP。
2. 单文件导入上限：图片 64 MB、音频 16 MB、音频总量 1.5 GB。
3. 主进程只做文件头校验，真实解码由渲染进程判定；头部合法但内容损坏的素材会在界面报错，且保存前的引用保护仍生效。
4. 内存数据仅本机单台 Windows 机器；未做 FPS 逐帧采样与 GPU 显存测量。
5. 暂存目录在 `userData` 下，与工程目录分离；只复制 `project.paper.json` 不会带走素材。
