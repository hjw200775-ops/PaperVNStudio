# V0.8.1 · 音频演出引擎（Audio Performance Engine）

本轮把 V0.8.0 的舞台演出从「只动画面」扩展到「画面与声音一起编排」，并且坚持一条底线：
**音频动作不进入 `stateAt()` 的副作用，只有可计算的音频目标状态才进。**

- 代码：`dist/audio.js`（引擎）、`dist/performance.js`（音频动作与目标状态）、`dist/player.js`（执行器）、`dist/app.js` + `dist/index.html`（编辑面板）
- 测试：`tests/audio-performance.test.cjs`（引擎）、`tests/performance.test.cjs`（动作与目标状态）
- 真实运行时：`scripts/v081-audio-engine-window.cjs`（引擎曲线）、`scripts/v081-audio-window.cjs`（剧情推进/存档/快进）

---

## 1. 审计结论（M1）

现有实现（V0.5 起）已经稳定：`HTMLAudioElement` + 单一 BGM 通道 + 音效通道池 + 语音通道，
`prefs`（用户偏好）与 `itemVolume`（本次播放音量）相乘得到最终音量，淡变用 30ms 定时器直接写 `el.volume`。
**没有 Web Audio API**，也没有解码缓存，所以「大型 WAV 全部进内存」的风险本就不存在（素材按需 `<audio>` 解码）。

因此本轮**不推倒重写**，只做加法：

| 缺口 | 处理方式 |
|---|---|
| 只有「旧曲淡出→新曲淡入」，没有真正交叉淡化 | 新增 `bgmCrossfade()`：两个通道并存，按曲线此消彼长 |
| 循环只能整曲（`el.loop`） | 新增循环区间：整曲 / `[loopStart, loopEnd]`，到点回跳并统计接缝 |
| 没有剧情音量，改剧情会覆盖用户设置 | 新增 `showVolume`（总线级），与 `prefs` 相乘、互不覆盖 |
| 没有 Ducking | 新增 `duckPush/duckPop/setDucking`，按计数持有，连续语音不抖 |
| 音效无法按「某条动作」停止 | 新增 `key` 通道表，同 key 复用/停止，超过 8 条丢最旧 |
| 语音被替换时没有统一收口 | `voicePlay` 先停旧再启新，`voiceStop` 释放 Ducking |

### 混音公式

```
最终音量 = Master × 用户分类音量（prefs）× 剧情音量（showVolume）
          × 播放音量（itemVolume）× Ducking（仅 BGM）
```

`prefs` 来自玩家设置面板（`localStorage`），`showVolume` 只由演出动作 `audio.bus.volume` 改写。
两者是两条独立链路：**剧情把 BGM 压到 20%，玩家设置的 80% 仍然是 80%**，下次开新场景自动回到 80%。

## 2. 音频动作模型（M4）

11 种动作，全部是纯数据，参数与取值范围在 `dist/performance.js` 的 `checkParams()` 里逐项校验：

| 动作 | 关键参数 | 终态（进 `stateAt`） |
|---|---|---|
| `audio.bgm.play` | 素材、音量、淡入、循环 | `audio.bgm = {audioId, volume, loop}` |
| `audio.bgm.stop` | 淡出时长 | `audio.bgm = null` |
| `audio.bgm.crossfade` | 素材、音量、时长、曲线（linear/equalPower）、循环 | 同上（新曲） |
| `audio.bgm.volume` | 目标音量、过渡时长 | `audio.bgm.volume` 插值 |
| `audio.bgm.loop` | 循环模式、区间 | `audio.bgm.loop` |
| `audio.sfx.play` | 素材、音量、key | —（一次性，不进终态） |
| `audio.sfx.stop` | key | — |
| `audio.voice.play` | 素材、音量、是否压低 | —（一次性） |
| `audio.voice.stop` | — | — |
| `audio.bus.volume` | 总线、音量、过渡 | `audio.buses[bus]` 插值 |
| `audio.ducking` | 开关、压低到 %、attack、release | `audio.ducking` |

### 为什么一次性动作不进终态

`stateAt()` 是纯函数，「跳过 = 播完」全靠它。音效与配音是**一次性外部副作用**：
如果把「播放过风铃」写进状态，跳过时就会重放全部历史音效——正是任务书禁止的行为。
所以：

- **BGM / 总线 / Ducking** 有终态，跳过时用 `applyAudioState()` 一次性落地（同一首不重启）；
- **SFX / Voice** 没有终态，只在动作起点执行；跳过、快进、读档一律不补播。

### 执行器（`dist/player.js`）

```
draw()
 ├─ enterAudio(mode)          逐句音频先落地（rebuild 时会 stopBgm）
 └─ runPerformance()
     ├─ runAudioPerformance() 按 schedule 的 start 挂定时器 → 到点调用引擎
     └─ PF.play()             画面 rAF
```

顺序很关键：反过来会让 `startSession` 的「清空 BGM」把演出刚起的音乐掐掉（这是本轮抓到的一个真 bug）。

跳过 / 快进：`perfSkip()` → 取消未执行的定时器 → `audio.applyAudioState(目标状态)`。
换句：`draw()` 开头同样先收口上一句（非阻塞淡变也按目标落地，不会停在半音量）。

## 3. 交叉淡化

```js
const gains = crossfadeGains(p, curve);   // linear: {out:1-p, in:p}
                                          // equalPower: {out:cos(pπ/2), in:sin(pπ/2)}
old.el.volume = channelVolume(old, gains.out);
new.el.volume = channelVolume(new, gains.in);
```

- 新曲**立刻开始播放**（不是等旧曲淡完），所以不会出现「旧曲消失了新曲还没响」的空档；
- 旧曲在新曲到位后才 `pause()` 并销毁，`retiring` 计数归零；
- 同一首 BGM 的「切换」请求不会新建实例，只做音量过渡与循环设置——这是防止双重 BGM 的关键；
- 目标素材解析失败时 `channel()` 返回 `null`，旧曲留在原位（继续播），不会静音。

实测（`release/audio-performance-benchmark.json`，真实 Chromium 解码）：

| 场景 | 结果 |
|---|---|
| 线性淡入 1.6s | 15 个采样点单调上升 0 → 0.80 |
| 等功率交叉 1.5s | 12 个中转采样 0 → 0.10 → 0.29 → 0.49 → 0.63 → 0.74 → 0.79，峰值 0.80（无尖峰） |
| 过渡期实例 | `bgm=1, retiring=1`；结束后 `retiring=0` |
| 连续 100 次切换 | 终态 `bgm=1, retiring=0, volume=0.80`，`prefs.bgm` 与 `buses.bgm` 均未被改写 |

## 4. 循环区间

`loopSpec` 三态：`off` / `all` / `region`。`region` 必须 `end > start`，否则退化为整曲。

播放路径：从曲首开始 → 到 `loopEnd` 回跳 `loopStart` → 反复。
回跳检查同时挂在 `requestAnimationFrame`（可见窗口，每帧）、`timeupdate`（媒体时钟，~4Hz）
与 400ms 定时器（兜底）上，取最先触发者。

**实测精度（不宣称采样级无缝）**：本机验收窗口处于无前台合成环境，rAF 不触发、定时器被平台节流到 ~1s，
8 秒 3 次回跳的接缝为 **平均 330ms / 最大 984ms**。代码在前台可见窗口下按帧检查，但本机没有取得前台样本。
如实记录，不做「无缝」声明。

## 5. Ducking

- 语音开始时 `duckPush()` 计数 +1，结束时 `duckPop()` -1；
- 计数为 0 才恢复，所以连续两句语音不会「抬起→压低」抖一次；
- `attack` / `release` 各自独立缓变（30ms 步进），`level` 是「压低到原来的多少」（默认 0.35）；
- 语音被替换（`voicePlay` 新的）时先停旧、释放一次持有，再重新持有，不会累积。

实测：BGM 0.80 → 0.28（约 35%）→ 语音结束回到 0.80，`active=false`。

## 7. 与旧工程、导出、流式素材的关系

- `schema 6`、`performance` 缺省 `null`、动作缺字段补默认值——旧工程不改一行仍能打开；
- `core.referencedAudioIds()` 现在会把演出里 `audio.*` 引用的素材算进去（本轮修复：
  只在演出中出现的 BGM 会被导出裁剪掉，运行时表现为「素材缺失」）；
- 标题音乐支持可选 `loopStart/loopEnd`：`checkTitleMusic` 校验区间，`toTitleMusic` 负责**保留**
  这两个字段（RC2 修复：此前规范化会把它丢掉，保存重开就变回整曲循环）；
- 导出仍是「自包含 HTML / 目录版 papergame://」两条路，音频与图片一样按引用裁剪后内嵌或落盘；
  播放器层只有 `<audio>`，不新增网络请求，也不把大型素材塞进 Base64 之外的新形态。

## 8. 已知边界

- 无多轨时间轴、无波形编辑、无音频关键帧（V0.8.2）；
- 循环接缝在 `precise` 模式下由音频线程负责（RC2 实测：正弦 30 次边界最长静音 0.021 ms）；
  `stream` 回退模式仍受页面可见性与定时器节流影响，不宣称无缝；
- 单位仍是「每个动作一条」，没有「音频组」概念；
- 配音仍是整段文件，不做按句切分或 TTS。

## 9. V0.8.1-RC2：混合播放、音乐槽与在线测量

### 9.1 两种播放模式，一条边界

| 维度 | `stream`（HTMLAudioElement） | `precise`（AudioBufferSourceNode） |
| --- | --- | --- |
| 适用 | 大文件、长语音、环境音 | 需要精确循环的 BGM、标题曲 |
| 内存 | 只留媒体缓冲 | 解码后整曲进内存（按预算） |
| 循环 | 原生 loop / 回跳检查 | 音频线程 `loopStart/loopEnd` |
| 淡变 | `volume` 属性 + 30 ms 定时器 | `AudioParam` 曲线排程 |
| 失败时 | —— | 回退 `stream`，`preciseReason` 写明原因 |

选择顺序：`loopMode` 显式偏好 → 解码预算 → 解码结果。任何一步失败都**回退**而不是静音。

### 9.2 音乐槽：标题曲与剧情 BGM 不可能同时存在

RC2 把标题音乐从「独立 `<audio>` + ticker」改成**同一个音乐槽**：

```
preciseBgm.owner ∈ { 'story', 'title' }
```

- `titlePlay()` 起新曲时，旧的（无论归属）在音频时钟上淡出并销毁；
- 剧情 BGM 起来时，精确槽里的标题曲作为交叉淡化的 `old` 自然退场；流式回退路径则显式淡出；
- `titlePause()` 记录 `offset` 后停止节点，`titleResume()` 从该偏移继续；
- `stopAll()` 同时清掉标题曲与剧情曲，`dispose()` 关闭自建的 `AudioContext`。

于是「双 BGM」「返回标题放错曲」「重复创建 AudioContext」在结构上不成立，而不是靠调用顺序保证。

### 9.3 内存：预算、串行解码与在途统计

```
budget = 64 MiB（可配）
估算   = 压缩体积 × 24（WAV × 2.2）
```

- **解码前**先按压缩体积估算解码后占用，超预算直接 `reason='budget'` 回退，不赌解码结果；
- **串行化**：同一时刻只允许一段在解（`decodeChain`），避免 N 个并发解码把峰值推成 N 倍预算；
- **淘汰**在解码前做（`cacheMakeRoom`），正在播的那条永不淘汰；
- 竞态：`loadSeq` token，过期结果直接丢弃（RC2 修复：过期结果曾被当成「回退流式」并真的播出来）；
- 快照里的 `audioMemory` 分别给出：缓存、在播解码缓冲、在途解码、峰值、被取消/被拒次数、流式通道数。

### 9.4 发布资源读取：只放开「读自己的素材」

精确模式需要 `fetch` 字节。改动只有三处，且都保持最小权限：

| 位置 | 改动 | 仍然不能做的事 |
| --- | --- | --- |
| 目录版游戏 `papergame://` | `supportFetchAPI: true`，CSP `connect-src 'self'` | 读 `content/` 之外的文件、任何网络请求 |
| 单文件游戏 `wanfeng://` | `supportFetchAPI: true`，CSP `connect-src data:` | 只认内联 data:，无网络 |
| 编辑器预览 `pvres://` | CSP `connect-src 'self'` | 会话目录之外 404，无网络 |

协议处理器本来就只服务白名单路径（`content/assets/...`、`assets/(images|audio)/<64位哈希>.<ext>`、
会话目录），`..` 与反斜杠一律拒绝，所以「放开 fetch」等于「允许读已经登记过的素材」。
`webSecurity`、`sandbox`、`site isolation` 一个都没关。

### 9.5 在线测量：三种证据分开记

| 证据 | 方法 | 能证明什么 |
| --- | --- | --- |
| 离线 PCM | `OfflineAudioContext` 渲染同一张图 | 算法与排程正确（不受机器负载影响） |
| 在线 PCM | 真实窗口 + `AudioWorklet` 在总线后采样 | 音频线程实际输出无接缝、不受渲染线程卡顿影响 |
| 操作系统回环 | 未采集 | ——（报告里明确写 NOT_RUN） |

RC2 的 `AudioWorklet` 采集最初失败，原因不是 `file://`，而是**统计没复位**：worklet 的计数器一直累积，
把两次播放之间的静音算成接缝。修法是 `port.onmessage('reset')` + 首样本不做跳变比较。
