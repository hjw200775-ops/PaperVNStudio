## 1. M2 完成后的状态

时间轴是现有演出系统的**编辑入口**（不是第二套游戏引擎）。本轮（M2-B）把预览从视觉提升到音视频：

- **统一时间基准**：视觉单调时钟 `anchorT+(now-anchorWall)/1000` 驱动音频事件扫描 `(lastT, t]`；
  BGM 精确循环仍由 AudioContext 时钟接缝；不累加固定帧增量、不依赖 rAF 命中音频边界。
- **音频事件调度**：`dist/timeline-preview-audio.js` 的 `createPreviewAudioDriver`（纯逻辑、可注入可测试）
  订阅 7 个预览事件 + onTick，复用 `perfAudioAction`；同一时间事件按 `schedule()` 稳定排序。
- **状态恢复**：`applyStateAt(t)` 落地「严格 < t」的历史累积（`stateAt` 的 `t ≤ slot.start` 即跳过语义），
  扫描触发「≥ t」的事件，边界互补、无重复无遗漏——任意时间开始/seek/循环回绕统一。
- **最小扩展**：`applyAudioState(state, options.offset)`（暂停继续恢复 BGM 位置），向后兼容。

## 2. 交接给 M3 的边界

### 2.1 时间轴已具备（M3 不应重做）

- 单节点多轨时间轴编辑：移动/拉伸/缩放/吸附/多选/批量移动/复制粘贴删除/撤销重做/保存重开。
- 真实音频波形摘要（只读，64 MiB 缓存复用，串行解码）。
- 实时音视频预览：播放/暂停/继续/停止/重播/任意起点/区间循环；一次性音频防重放；竞态与生命周期保护。
- 数据模型：`node.performance.actions[].start`（可选绝对秒，0–86400），旧工程无损打开。

### 2.2 M3 方向：发布运行时一致性（本轮禁止提前进入）

时间轴编辑的 `start` 字段已在 `schedule()` 里被优先读取，因此**编辑器预览与发布游戏的排程本身已共用同一份数据**。
M3 需要验证并补齐的是「发布运行时」这一侧的闭环，而非再改时间轴：

1. **发布游戏对显式 `start` 的执行一致性**：导出播放器（`player.js`/`game-html.js`）逐句播放时，
   含显式 `start` 的动作是否与编辑器时间轴预览逐字段一致（终态、并行、阻塞）。
2. **读档/快进/跨句的音频状态对齐**：预览用 `applyStateAt` 落地「< t」的累积，发布游戏读档路径
   （`enterAudioInto(rebuild)` / `applyAudioState`）是否与预览的 BGM 位置/音量/循环语义对齐；
   时间轴预览的 `offset` 恢复（暂停继续）是否需要下沉到发布读档路径。
3. **跨句时间轴（方案 B）**：数据模型已预留（`{nodeId, actions[]}`），若做需评估场景共享播放头，
   本轮未做。
4. **音画同步量化验收**：M2-B 采集了「计划触发时间 vs 在线音频图 RMS」证据，未做逐事件毫秒级
   偏差统计；M3 若要宣布「采样级同步」，需补 P95 偏差测量并注明 AudioContext 时间 ≠ 扬声器发声时间。

### 2.3 冻结模块（M3 同样不要擅改）

`dist/performance.js` 核心调度与求值、`dist/player.js`、`dist/core.js` 迁移语义、
V0.7.6 资源存储。`dist/audio.js` 核心音频引擎：仅允许与 M2-B 同等的「最小能力 + 向后兼容」扩展，
先写复现证据与影响范围再改。

## 3. 已知限制（M2-B 遗留，随 M3 收敛）

1. **暂停继续的 BGM 位置恢复是有损上限**：精确模式（AudioBufferSourceNode）原生支持 offset，
   流式回退用 `currentTime` 恢复；`applyAudioState` 无 offset 时从曲首起播（沿用 V0.8.1 `rebuild` 语义）。
   中途进入「正在淡入/交叉淡化」的 BGM 无法逐样本无损还原中间增益，定义的产品语义是「以目标状态瞬时恢复」。
2. **一次性音频恢复语义**：暂停即停止正在播的 Voice/SFX；继续从暂停点之后重新触发，
   不续播「已开始未播完」的 Voice 剩余部分（明确的产品语义，非无损恢复）。
3. **区间循环与 BGM 素材循环分离**：A 时间轴区间循环（编辑器临时状态）与 B 素材精确音乐循环
   （V0.8.1）各自计数，互不覆盖；时间轴回绕时 BGM 按区间起点目标状态重建。
4. **掉帧跨越事件采用「执行」规则**：视觉时钟掉帧跨越一次性事件时按 `schedule()` 顺序补触发
   （不无声遗漏），因此极端掉帧下一次性音频会集中触发而非丢弃——这是明确的产品语义。
5. **在线音频证据边界**：采集的是 AnalyserNode（总线后/master 前）的时域 RMS，证明「有真实输出」；
   不是扬声器/操作系统回环，不把 AudioContext 调度时间等同于实际发声时间。
