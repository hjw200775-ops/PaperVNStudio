# V0.7.6 工程资源架构：运行时不再持有 Base64

基线 `d0582cf`（V0.7.5）。V0.7.5 解决了发布端的 64 MB 墙，但编辑器的运行时工程对象仍然把每张图、每首曲都当 data URI 揣在内存里——这是 1 GiB 工程失败的直接原因。

## 一、诊断：data URI 是在哪一步回来的

磁盘从 V0.3 起就是内容寻址（`assets/images/<sha256>.png`），**打开工程时** `diskToRuntime` 把每个文件读成 `data:` 地址塞进 `assets[].data`。之后所有环节都以它为真身：

| 环节 | 之前 | 现在 |
| --- | --- | --- |
| 打开工程 | 读文件 → base64 → `data:` | 读文件校验 → `paper://app/asset/<相对路径>`，只读文件头取尺寸 |
| 编辑器舞台 | `<img src="data:…">` | `<img src="paper://app/asset/assets/images/…">` |
| 撤销 / 重做 | clone 整个工程（含全部 base64） | clone 元数据（几十 KB） |
| 自动保存 / 保存 | `JSON.stringify` 整个工程 | 只写元数据；素材按需读原文件复制 |
| 完整预览 | 工程对象经 IPC（含 base64） | 同上，资源由主进程从磁盘读 |
| 游戏导出 | 工程对象（含 base64） | 同上 |

`C.migrate` 对 schema 5 原来是 `clone(input)` 后再归一，1 GiB 工程在这一步就直接抛 `Invalid string length`。现在 schema 5 原地归一，不再深拷贝。

## 二、素材地址：`paper://app/asset/…`

一度试过独立 scheme（`paperasset://`），但 sandbox 页面里 `<img>` 与 `fetch` 都被拒（`Failed to fetch`，handler 根本没被调用）。改成挂在**已验证可用的 `paper://`** 下：

```
paper://app/asset/assets/images/<sha256>.png
paper://app/asset/assets/audio/<sha256>.ogg
```

- 同源：CSP 的 `'self'` 直接放行，不新增 scheme 特权；
- `paper` handler 新增 `/asset/` 分支：路径必须匹配 `assets/(images|audio)/<64位哈希>.<ext>`，`path.resolve` 后再校验前缀，出不去当前工程目录；
- 内容寻址 → 文件名不可变，返回 `immutable` 长缓存；
- `state.currentDir` 为空（没开工程）一律 404。

## 三、保存与另存为

- 保存：`diskAssets` 遇到 `paper://app/asset/…` 直接读原文件、校验哈希与文件名一致，不重新编码；写入后把运行时 `data` 原地换成新地址。
- 另存为 / 新建：新增 `sourceRoot` 参数。素材还在旧目录，读源用旧根、写新文件用新根——**这是本轮修掉的真 bug**：改 URL 之前，另存为会把素材整体丢掉（`used` 集合里没有文件可写）。
- 去重：新增 `assetContentKey()`，已落盘的用 `sha256`、内存里的 data URI 现算，两种表示可互比。

## 四、导出与单文件 HTML

- 目录版 / ZIP：`writeContentAsset` 支持从 `paper://app/asset/…` 读原文件，逐张复制、内容寻址；先按 `referencedImageIds`/`referencedAudioIds` 裁剪（V0.7.5 已有）。
- 单文件 HTML：导出前把受控地址读回 data URI（`fetch` → `FileReader`），**只在这一步做 Base64**；素材总量超过 200 MB 时直接给中文提示，建议改用独立游戏目录，不会让编辑器卡死。
- 单文件视图默认全量内嵌（不再按引用裁图）：作者明确选「单文件」时优先保证不缺图；引用裁剪由发布构建器负责。

## 五、实测（本机 SSD）

| 项目 | V0.7.5 | V0.7.6 |
| --- | --- | --- |
| 《晚风》示例运行时工程 JSON | ~21 MB | **34 KB** |
| 舞台图片加载 | data URI 解码 | `paper://app/asset/…`，3/3 张 `naturalWidth > 0`，单个请求 1.9 MB |
| 保存后磁盘工程 | — | 无 `data:image`，素材仍按 `<sha256>.png` |
| 重开工程 | — | 图片仍正常显示 |
| 目录版导出（示例） | 154 KB 页面 / 8 图 / 3 曲 | **157 KB 页面 / 8 图 / 3 曲**，启动 297 ms |

`npm run check` 全绿。

## 六、没做完的（明确列出）

1. **导入还没落盘**（任务里的 M3）。当前导入仍是「读成 data URI → 存进内存 → 保存时写盘」。所以：
   - 已保存素材是 `paper://` 地址、新导入的是 data URI，同一文件**跨表示不会复用**（`audio-store` 里已把这条写成明确断言 `reused === false`，而不是放宽成永真）；
   - 单图上限从 12 MB 放开到 64 MB、音频总量到 1.5 GB，但导入一张 64 MB 图仍要过一次 base64。
2. **1 GiB 工程未验证**。本轮只把「打开、编辑、撤销、保存、预览、导出」的表示改轻；一次导入上千张图仍会在内存里堆出 1 GiB 级 base64。要真支持 1 GiB，需要把导入也改成流式落盘 + 哈希，这依赖主进程导入通道，本轮没做。
3. **内存峰值未采样**。没有在主进程调 `app.getMetrics()`，不给估算值。
4. 三个《晚风》Alpha 工程仍未同步，真实作品验收未完成。
5. 单文件 HTML 的图片不再按引用裁剪（见第四节说明），发布包仍然裁剪。
