# V0.7.6 工程资源架构：流式导入 + 内容寻址 + 运行时零 Base64

基线 `1ba3fd3`（V0.7.6-M2）。M2 把**已落盘**素材改成受控 URL，解除了打开/保存/撤销时的 Base64 序列化瓶颈；M3 把**导入**这一环也搬出渲染进程，形成完整链路：

```
待导入（磁盘原文件）
   ↓ asset:stage 流式读取 + 分块 SHA-256
暂存 paper://app/staging/<sha256>.<ext>（userData/asset-staging）
   ↓ 编辑器只拿 URL / 哈希 / 大小 / MIME / 尺寸或时长
工程引用（撤销栈、历史快照、自动保存都持有同一个 URL）
   ↓ 保存 / 另存为：按内容哈希流式复制，工程 JSON 只留相对路径
正式保存 paper://app/asset/assets/{images,audio}/<sha256>.<ext>
```

渲染进程**从头到尾不持有素材字节**。桌面版所有导入入口（背景、角色立绘、表情、标题背景、CG、BGM、SFX、Voice）都走主进程暂存；`FileReader.readAsDataURL` 只剩浏览器版回退与单文件 HTML 水合两处，由 `tests/asset-lifecycle.test.cjs` 静态锁死。

## 一、M3-1 流式暂存（`desktop/asset-staging.cjs`）

- 主进程 `asset:stage`：`createReadStream` → `Transform`（逐块 `hash.update`、保留 1 MB 头部样本）→ `createWriteStream(tmp)`，**从不把整文件读进内存**，也不生成 Base64。
- 完成后按内容哈希原子改名到 `userData/asset-staging/<sha256>.<ext>`；同内容文件已存在则只删临时文件，磁盘占用不增长。
- 返回 `dataUrl`（受控 URL）、`sha256`、`size/bytes`、`mime`、`ext`、图片 `width/height` 或音频 `duration`，以及 `staged: true`。
- 头部校验只判「像不像可解码素材」：PNG/JPEG/WebP 魔数与 IHDR、WAV 的 `RIFF/fmt/data` 块头、OGG/FLAC/MP3 魔数；真实解码交给渲染进程的 `<img>` / `Audio`。
- 批量：`stageFiles` 逐文件汇报 `index/count/phase/percent`，单文件失败只记入 `errors` 并继续；`asset:cancelStage` 可取消，取消时删除 `.tmp-`，不留半成品。
- 界面：`asset:stageProgress` → `#assetProgress` 进度条与取消按钮；错误逐条 toast。主进程做 IO，编辑器主界面不会因大文件长时间卡住。
- 协议：`paper://app/staging/<64位哈希>.<ext>` 挂在已验证可用的 `paper` scheme 下，与 `/asset/` 同样做哈希白名单与 `path.resolve` 前缀校验；保存前的预览会话也能直接读暂存文件。

## 二、M3-2 内容寻址与跨表示精确去重

统一标识是 **SHA-256**，与文件名、目录、表示形式无关：

| 表示 | 取值来源 |
| --- | --- |
| 新导入（暂存 URL） | 流式计算出的 `sha256` |
| 已落盘（`paper://app/asset/…`） | 磁盘元数据里的 `sha256`，文件名即哈希 |
| 旧工程（data URI） | `ensureContentHashes()` 用 WebCrypto 补算；`assetContentKey()` 在 Node 侧现算 |
| 暂存 URL 但缺 `sha256` | 从 URL 解析哈希 |

- `C.assetForImport`：按 `sha256 + kind` 查重（同一张图当背景和当角色仍是两条素材，避免用途被带回）。
- `C.assetForAudioImport`：按 `sha256` 查重，分类合并（同一文件可同时作 BGM / SFX / Voice）。
- `tests/audio-store.test.cjs` 里描述未实现行为的 `assert.equal(reused.reused, false, ...)` **已恢复为** `assert.equal(reused.reused, true, '跨表示同内容精确复用')`；没有删测试、没有放宽断言。
- 覆盖矩阵：同一文件重复导入、改名同内容、同名不同内容、已保存 vs 新导入、图片/音频各自语义、保存/重开/另存为后仍复用。见 `tests/asset-lifecycle.test.cjs` 与 `tests/asset-staging.test.cjs`。

## 三、M3-3 生命周期与引用保护

- 状态：`待导入 → 暂存 → 工程引用 → 正式保存`。暂存文件是不可变内容寻址文件，保存时用 `copyFileSync` 流式复制到工程目录并核对大小；工程 JSON 与素材同批原子写入，不会产生指向不存在文件的地址。
- 清理规则：渲染进程 `stagedRefs()` 扫描**当前工程 + `past` 撤销栈 + `future` 重做栈**里所有素材的暂存哈希；主进程 `asset:gc` 只删不在这份保护集合里、且已过期的文件，缓存未命中时宁可不删。
- 覆盖场景（真实 fs 测试）：导入后未保存、取消、失败中断、撤销与重做、删除素材后撤销、保存失败后重试、关闭工程不保存、异常退出重启（`staging.reset()`）、另存为（`sourceRoot` 从旧目录复制）。
- 保存/另存为/新建/自动保存/打开都会重新计算保护集合；`before-quit` 时在没有渲染进程引用的前提下整体清理。

## 四、保存、预览与发布

- 打开：`diskToRuntime` 默认只 `statSync` 校验大小（可选 `verify` 才读文件算哈希），避免每次自动保存把 1.5 GB 素材重读一遍；运行时 `data` 是 `paper://app/asset/…`。
- 保存：`fileSource()` 对已落盘/暂存素材只取 `stat`，跨目录才复制；`writeAssets` 用 `copyFileSync` 流式复制，不把素材读进 Buffer。
- 预览：`writePreviewAsset` 支持 `paper://app/staging/…` 与 `paper://app/asset/…`，直接读磁盘写会话目录，播放器按 `pvres://` 按需加载。
- 发布：目录版 / ZIP 按 `referencedImageIds`/`referencedAudioIds` 裁剪后复制；`game:export` 的 `folder` 类型在 M3 回归中修掉了一处真 bug——旧代码只认 `portable`，界面选「独立游戏目录」会被静默降级成 ZIP 包，现在白名单与产物后缀都与 `game-builder` 一致。
- 单文件 HTML：仍受 200 MB 限制。M3 把守卫改成无条件执行（旧代码只在素材是受控 URL 时检查，纯 data URI 旧工程会绕过并可能拼出超大字符串）；超限给出中文提示引导到独立游戏目录 / ZIP，在真实窗口对 1 GiB 工程验证通过。

## 五、1 GiB 实测（`release/large-project-acceptance.json`）

可复现生成脚本 `scripts/make-large-project-m3.cjs` 产出 **1,576,200,076 bytes 去重后素材**（100 张真实可解码 PNG + 104 段 44.1 kHz 立体声 PCM WAV，204 个不同哈希），12 章 / 576 节点 / 6 角色，背景、立绘、表情、BGM、SFX、Voice 都有真实引用；不用空文件、稀疏文件或重复素材凑体积。素材本体不进 Git。

真实 Electron 编辑器窗口（`scripts/m3-acceptance.cjs`，CDP 取证）完成：导入、打开、编辑剧本、切换章节/场景、背景与立绘解码、BGM/SFX/Voice 播放、撤销重做、保存、关闭重开、完整预览、目录版导出、启动导出游戏并验证 `papergame://` 资源加载，外加单文件 HTML 上限引导。全程无 `Invalid string length`、无 OOM / 渲染进程崩溃、运行时工程 JSON 无 Base64、素材哈希与总量前后一致、重复导入不增加磁盘占用。

持续采样 214 个点（CDP 114 + tasklist 100），覆盖全部 12 个阶段：

| 指标 | 实测峰值 |
| --- | --- |
| 主进程（Browser）工作集 | 514.8 MB |
| 渲染进程（Tab）工作集 | 324.5 MB |
| 所有 Electron 进程总工作集 | 1,118 MB |

> Electron 的 `ProcessMetric.type` 把渲染进程标为 `Tab`，`memory.workingSetSize` 单位是 KB，采样脚本已换算为字节；`release/memory-profile.json` 记录了方法、机器配置、逐阶段峰值、各项耗时与明确列出的未测量项。

代表性耗时（本机 SSD，含窗口启动与构建子进程）：打开 1.4 s、保存 1.1 s、重开 3.0 s、预览启动 4.0 s、目录版导出 4.0 s、导出游戏启动 2.3 s。

## 八、仍有的边界（不夸大为已解决）

1. 单文件 HTML 保持 200 MB 上限，1 GiB 工程按设计走目录版 / ZIP，不强行支持。
2. 单文件导入上限：图片 64 MB、音频 16 MB、音频总量 1.5 GB；更大的单文件需在外部预处理。
3. 真实解码由渲染进程的 `<img>` / `Audio` 判定，主进程只做文件头校验；损坏但头部合法的文件会在导入后由界面报出，且不会写进工程（保存前引用保护仍生效）。
4. 内存数据只来自本机单台 Windows 机器；不同 GPU / 第二台机器的基线未测，报告里明确列为未测量。
5. 暂存目录在 `userData` 下，与工程目录分离；移动/备份工程时应使用「另存为」或复制整个工程目录，单复制 `project.paper.json` 不会带走素材。
