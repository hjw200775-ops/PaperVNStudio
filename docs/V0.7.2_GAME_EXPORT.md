# V0.7.2 通用独立游戏导出

基线 `86e9884`（V0.7.1），版本 `0.7.2`。上一版把《晚风经过二楼走廊》做成了独立包，但只有开发者能构建；这一版把构建能力搬进纸间本身：**任何作者都能在图形界面里把自己的工程导出成 Windows 游戏，不需要 Node.js、Electron 或 npm**。

不在本轮范围：多槽存档、剧情变量、AI 剧情助手、AI 生图、TTS、Live2D、macOS / Linux 导出。

## 一、用户怎么用

1. 打开工程（工程目录或旧 `.paper.json` 导入都可以）。
2. 点右上角 **游戏发行**。
3. 填「游戏发行」面板：游戏名称（默认取工程名称）、作者、版本、版权；按需导入图标；设置默认窗口大小、是否允许缩放、窗口 / 全屏。
4. 选发行形式（ZIP 解压版 / 单文件便携 EXE）→ 点 **导出 Windows 游戏…** → 选一个**新的空文件夹**。面板会显示每个真实构建阶段、进度、错误；可随时取消。

界面截图（自动化验收时截的真实窗口）：`docs/screenshots/v072-publish-settings.png`（发行设置）、`v072-icon-import.png`（图标导入预览）、`v072-export-progress.png`（构建中）、`v072-export-result.png`（完成）、`v072-publish-b.png`（另一个工程的回读）。

## 二、发行设置是工程内容

字段（`p.publish`）：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `gameName` | 空 → 用工程标题 | 游戏标题页与 EXE 产品名都用它 |
| `author` | 空 | EXE 的 CompanyName、版权缺省值 |
| `version` | `1.0.0` | 游戏版本，和纸间自身版本无关 |
| `copyright` | 空 → 自动生成 | `Copyright © 年份 作者或作品名` |
| `icon` | `null` | `{name, data: data:image/png, width, height}`，512 见方 |
| `window` | `1280×840 / 可缩放 / 窗口` | 宽 640–3840、高 480–2160，模式 `window`/`fullscreen` |
| `releaseId` | 空 → 由工程 id 推导 | 存档目录名，见第六节 |

- 保存、另存为、JSON 备份、撤销重做都带上它（`snapshot()` 里显式克隆 `publish`；磁盘格式新增可选字段）。
- **旧工程与网页版工程**缺这个字段时按默认值补齐，不升 schema 版本号（仍是 5），HTML 导出完全不受影响。
- 图标内嵌在工程 JSON 里（≤4MB）而不是新增一类工程文件：备份、撤销、另存为的行为与其它工程数据一致，不需要额外的文件生命周期管理。

## 三、游戏图标

- 支持 **PNG / JPEG / ICO**。PNG、JPEG 在渲染进程用 canvas 归一到 512×512：**等比缩放、透明留边、不拉伸不裁切**；ICO 由主进程取其中最大的一档（只接受 PNG 压缩条目，旧式 BMP 条目会明确提示换格式，不做「看起来导入成功但很糊」的降级）。
- 预览与「恢复默认」都在面板里；没导入时用随包的纸间默认图标（`desktop/game-shell/default-icon.ico`）。
- 构建时用 Electron 的 `nativeImage.resize` 生成 16/20/24/32/40/48/64/128/256 九档，再用 rcedit 写入 EXE 图标资源。
- 生效验证：验收读 PE 资源表确认两套产物的图标组都是 9 档（原版 `electron.exe` 只有 4 档），且自定义图标的 ICO 字节数与默认图标不同；清单里记录 `icon.source = custom|default`。
- 失败提示：空文件、超过 8MB、扩展名与内容不符、无法解码、ICO 是 BMP 条目，都会在面板里给出具体原因。

## 四、播放器交互（P0）

上一轮交付的试玩包能玩，但玩家按住拖动时会看到浏览器原生的蓝色选区，拖动立绘/背景还可能拖出一张半透明缩略图。根因不是壳没锁好，而是**播放器本身就是一张网页**，而 `dist/player.js` 里的 `paperPlayerCSS` 从没写过 `user-select`，`<img>` 也没设过 `draggable`。壳只负责网络与权限，不会改变 Chromium 的默认手势。

修复分三层，都落在共享播放器上，所以预览、HTML、ZIP、单文件自动一致：

| 位置 | 规则 | 作用 |
| --- | --- | --- |
| `paperPlayerCSS` | `#titleScreen,#gameRoot,.overlay,#msg{user-select:none}` | 标题页、舞台、台词、选项、菜单一律不出选区 |
| `paperPlayerCSS` | `#titleScreen img,#gameRoot img,.overlay img{-webkit-user-drag:none}` | 展示图片不参与原生拖拽 |
| `paperPlayerCSS` | `input,textarea,select{user-select:text}` | 设置面板的滑块、复选与将来的输入框照常可用 |
| `paperPlayer` | 图层 `img.draggable=false` | 运行时创建的立绘同样不可拖 |
| `paperPlayer` | `document` 上 `dragstart` 兜底（限定三个容器，排除输入控件） | CSS 没覆盖到的新元素也不会被拖成文件 |
| `dist/export.js` | `#titleBgImg` 带 `draggable="false"` | 静态标题图从 HTML 层面就不可拖 |

两条边界，都是有意为之：

- **不碰 `pointer-events`**。`#layers` 靠 `pointer-events:none` 让点击穿透到舞台，一旦为了「禁选」把它改成 `auto`，点击立绘就不会推进剧情了。禁选只用 `user-select` / `-webkit-user-drag`。
- **不把规则绑在对话框样式上**。作用于 `#gameRoot`、`#titleScreen`、`.overlay` 这些结构容器，V0.8 的对话框快捷栏与 UI 设计器放进这些容器就自动继承，不需要再改一遍。

编辑器内试玩走的是另一套舞台（`dist/style.css` + `dist/app.js`），所以单独加了一条 `body.playing #stage, body.playing #stage *{user-select:none}`：**只在试玩时禁选**，创作模式照旧可以选中台词、拖动与缩放素材。

顺带修掉一个被拖动掩盖的问题：原来 `#stage` / `#scene` 的 `click` 不区分手势，按住拖动再松手会被当成点击，剧情无故跳一句。现在两边都记录 `pointerdown` 坐标，位移超过 8px 就不推进；选项按钮本身 `stopPropagation`，不受影响。

实测（真实鼠标事件，五个载体一致）：标题拖选/双击 0 选区；从台词拖到立绘 0 选区且不推进；按住立绘拖动 0 选区、0 次 `dragstart`、不推进；单击正好前进一句；选项可点进分支；设置面板音量滑块可拖动；编辑器创作模式仍能选中台词。

## 五、构建流程

```
工程快照（结构化克隆，构建期间继续编辑也不影响本次输出）
  → 检查（schema/素材/剧情引用，有 error 就拒绝导出）
  → 生成播放器内容（dist/game-html.js，标题替换为游戏名称）
  → 播放器壳（desktop/game-shell + content/index.html + game.json + 许可说明）
  → 图标（9 档 ICO）
  → 运行时（复制当前 Electron，排除编辑器自己的 app.asar / toolchain）
  → 版本与图标写入（rcedit）
  → ZIP（自写 UTF-8 ZIP 写入器） 或 单文件便携 EXE（NSIS 自解压）
  → manifest（大小、SHA-256、版本、签名状态、图标来源、阶段耗时）
```

实现细节：耗时步骤（复制运行时、rcedit、ZIP、NSIS）在 `desktop/game-pack-worker.cjs` 子进程里跑。主进程同步做这些会把事件循环占满，界面卡住、取消 IPC 进不来——这是实测踩到的坑，不是设计洁癖。取消 = 杀子进程，目标文件在最后一步之前不会被碰。

保护措施：

- **只在临时目录里构建**，成功后才移动到目标位置；失败/取消时删除临时目录，用户已有的同名产物保持原样。
- 目标已存在时弹「覆盖 / 选择其他目录 / 取消」，默认不覆盖。
- 构建期间主进程只允许一个任务，重复点导出会得到「已有导出任务在进行」。
- 取消：阶段之间与复制文件过程中都会检查；界面上的取消会持续重试，直到主进程真正收到（防止工程快照还在传输时点取消落空）。
- 真实阶段与错误：进度条、阶段列表、耗时都来自主进程回报；错误原文显示在面板里。

## 六、运行时与构建组件（本版核心）

| 组件 | 来源 | 缺失时 |
| --- | --- | --- |
| Electron 运行时 | **正在运行的这个纸间自己**：`process.execPath` 所在目录。开发环境是 `node_modules/electron/dist`，打包后是安装目录 | 不会缺；检测不到时直接说明「运行时目录不完整」 |
| rcedit | `resources/toolchain/rcedit/rcedit-x64.exe`（打包后）或 `vendor/toolchain/…`（开发） | 拒绝导出并提示运行 `npm run tools:prepare`（无法写图标/版本就不假装能写） |
| NSIS | `resources/toolchain/nsis/makensis.exe`（同上） | 仍可导出 ZIP；单文件选项置灰并说明缺 NSIS |
| ICO / ZIP | 代码内实现（nativeImage + 自写 ZIP） | 不依赖外部工具 |

- `npm run tools:prepare`（`scripts/prepare-game-toolchain.cjs`）从**本机已有缓存**收集 electron-builder 下载过的 NSIS 与 electron-winstaller 自带的 rcedit，整理到 `vendor/toolchain/`（约 3.0MB）。打包纸间时通过 `extraResources` 进 `resources/toolchain`，随程序分发。
- 不联网下载大型依赖：Electron 不重复下载（用自己），NSIS 只从本地缓存收集；缓存缺失时给出明确指引，不在后台偷偷下载。
- 已准备完整组件时，**ZIP 导出完全离线**；单文件版需要 NSIS，已随包分发，同样离线。
- 没有任何 `F:` / 盘符硬编码；打包后的纸间不再依赖 `node_modules`。

## 七、作品身份与存档

`releaseId` = `publish.releaseId`（合法则用）→ 否则由工程 id 生成 Slug（小写字母/数字/连字符；太短的 id 补 8 位哈希）。

| 场景 | 结果 |
| --- | --- |
| 同一工程重复导出 / 升级版本 | 同一 `releaseId`，继续读旧存档 |
| ZIP 与单文件便携版 | 同一 `releaseId`，共用存档 |
| 移动 / 改名游戏目录 | 存档在 `%APPDATA%\PaperVNStudio-Game-<releaseId>`，不受影响 |
| 两个不同工程、标题相同 | 工程 id 不同 → `releaseId` 不同 → 存档隔离 |
| 复制内置示例 | 现有规则给新工程 id → 新 `releaseId` |
| 另存为 | 按现有规则保留工程 id（视为同一作品）→ 共用存档 |

存档节点失效时，播放器仍按原有逻辑给出具体原因（哪一句被删除 / 路径失效），不静默删除原数据。

编辑器、内置示例、完整预览与正式游戏的存储彼此独立：编辑器用默认会话，示例用 `persist:papervn-sample` 分区，预览是 `file://`，游戏是 `papergame://game` + 自己的 userData 目录。

## 八、发行信息与安全

- EXE 写入：ProductName / FileDescription / CompanyName / LegalCopyright / LegalTrademarks / OriginalFilename / InternalName / FileVersion / ProductVersion。
- 文件名合法化与显示名称分开：文件名替换 `\ / : * ? " < > |`、去掉结尾空格与点（保留中文与空格），显示名称原样写进版本资源与窗口标题。
- 游戏端保持沙箱：`sandbox` + `contextIsolation` + 禁用 Node、无 preload、无 IPC；`papergame://` 白名单只服务 `content/index.html`；CSP `connect-src 'none'`；所有 http(s) 请求取消。
- 出包只含播放器壳、`content/`（HTML + game.json）、Electron 运行时、LICENSE、作者与许可说明、试玩说明。
- **版本号有两套值**：作者填的（`p.publish.version`）原样写进 `manifest.game.version` 与文件名；EXE 的版本资源只接受四段数字，由 `numericVersion()` 取每段的前导数字再补齐——`0.7.2-test → 0.7.2.0`、`1.2.3-beta.1 → 1.2.3.1`、`2 → 2.0.0.0`、空或无法解析 → `1.0.0.0`。实际写进 PE 的四段数字单独记在 `manifest.exeVersion`，验收用 `scripts/pe-version.cjs` 直接读 PE 资源比对。预发布后缀不会出现在文件属性里，界面的版本输入框下有提示，不阻塞导出。
- manifest 记录产物大小、SHA-256、游戏名/作者/版本/发行标识、图标来源、Electron 版本、构建阶段耗时、签名状态。
- 签名：沿用 `CSC_LINK` / `CSC_KEY_PASSWORD`（electron-builder 路径），本轮构建器用 rcedit 写资源、不自行签名；没有证书时 manifest 写 `signed: false`，试玩说明里提示可能出「未知发布者」，**不要求用户买证书，也不阻塞导出**。

## 十、已知限制

- 单文件便携版每次启动都要自解压（本机约 8–10 秒），首次可能被杀毒软件多扫一会儿。
- 构建在本机串行执行，导出期间不要关闭纸间；没有后台队列。
- 图标统一归一为 512 见方 PNG（等比留边），不接受多分辨率 ICO 里的 BMP 条目。
- 工程上限沿用现有规则（20000 节点 / 1000 图片 / 96MB 音频），超限会在「检查」阶段报错。
- 未签名；没有自动更新；只做 Windows x64。
- 打包版验收用 `--skip-portable`（单文件版在开发环境完整验证）：打包版再跑一次 NSIS 要三分钟，本轮按「ZIP 阶段通过后再验证单文件」的顺序记录。
- 首次导出的 EXE 可能被杀毒软件扫描几十秒，属正常现象。
- `release/game/` 下 V0.7.0/0.7.1 的《晚风》包是历史发行产物，本轮按「保留历史产物」没有重建；它们复用同一份 `paperPlayerCSS`，重新运行 `npm run game:build` 即可带上交互修复。

## 十二、命令与测试分层

```bash
npm run tools:prepare                 # 从本机缓存收集 rcedit + NSIS 到 vendor/toolchain
npm run export:acceptance             # 开发环境：两套工程走 GUI 导出 + 真机游玩验收
npm run export:acceptance:packaged    # 已打包的纸间（release/win-unpacked 或 release/pkg*）再跑一遍
npm run interaction:acceptance        # 播放器交互：5 个载体上的真实鼠标手势
npm run interaction:acceptance:packaged
npm run check                         # 逻辑测试与静态检查（含交互规则）
node scripts/game-export-smoke.cjs zip       # Electron 内部直接调构建器（排障用）
node scripts/game-export-smoke.cjs portable
```

npm run tools:prepare
node scripts/build-win.cjs portable --dir     # 只出 win-unpacked，用于验收
