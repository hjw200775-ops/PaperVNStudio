# V0.8.0 · 舞台演出系统（Stage Performance Engine）

本文说明 V0.8.0 新增的「演出」层：它解决什么问题、数据长什么样、运行时怎么算、为什么这样算、
以及与 V0.7.6 既有机制（逐图层效果、流式素材、单文件导出）如何共存。

- 代码：`dist/performance.js`（运行时）、`dist/app.js` 的「舞台演出编辑」区块（编辑器）、
  `dist/player.js` 的「舞台演出」区块（播放器）
- 单测：`tests/performance.test.cjs`
- 真实窗口验收：`scripts/performance-window-smoke.cjs`
- 编辑器教程：`docs/STAGE_PERFORMANCE_GUIDE.md`

## 1. 为什么不是「又一个效果系统」

V0.7.x 的 `effects.js` 回答的是**一句之内、单个图层**的属性插值：这句里背景从 100% 推到 108%，
这个立绘从右边飘进来。它的模型是「属性 + 起止 + 时长」。

要做舞台演出，需要的是另一种东西：**一串有先后关系的动作**——角色 A 从左边进来（阻塞），
背景同时交叉淡化到夜晚，镜头推近，然后等 0.5 秒，再让 B 淡出。这里面有并行、有顺序、
有「这一句演完之前不许推进剧情」、还有跨句延续（上一句把镜头推进了，这一句还在推近的状态里）。

硬把这两种语义塞进同一套数据结构，只会让旧工程的语义变得不可预测。所以 V0.8.0 的做法是：

| | `effects.js`（V0.7.x） | `performance.js`（V0.8.0） |
|---|---|---|
| 粒度 | 单个图层的属性插值 | 一串动作（角色 / 背景 / 镜头 / 全屏 / 等待） |
| 关系 | 无（各效果独立） | 顺序 / 并行 / 延迟 / 阻塞 |
| 作用域 | 一句之内 | 一句之内 + 跨句累积 |
| 渲染目标 | 外层 `.visual-layer` 的 transform/filter | 内层 `.pf-frame` 的 transform/opacity + 舞台镜头 + 覆盖层 |
| 对剧情推进的影响 | 无（纯视觉） | 可阻塞（`blocking`） |

两套东西同时存在、同时生效，互不覆盖：**效果写外层，演出写内层**。旧工程一行不用改，
`performance` 缺省为 `null`。

## 2. 数据模型

一段演出挂在一个剧情节点上：

```json
{
  "performance": {
    "version": 1,
    "actions": [
      { "id": "pa1", "type": "character.show", "target": "char:lin_you",
        "params": { "side": "left" },
        "duration": 1.0, "delay": 0, "easing": "easeOut",
        "blocking": true, "mode": "after", "enabled": true }
    ]
  }
}
```

字段语义（全部可序列化，不含函数、不含 DOM 引用、不含定时器）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 节点内唯一；复制动作时重新生成 |
| `type` | string | 14 种动作之一，见下表 |
| `target` | string | 语义目标：`char:<characterId>` / `bg` / `''`（舞台） |
| `params` | object | 动作参数，按类型校验取值范围 |
| `duration` | number | 0–30 秒 |
| `delay` | number | 0–30 秒，相对本动作的起点 |
| `easing` | string | `linear` / `easeIn` / `easeOut` / `easeInOut` |
| `blocking` | boolean | 是否让剧情推进等它演完 |
| `mode` | string | `after`（接在上一动作结束后）/ `parallel`（与上一动作同时开始） |
| `enabled` | boolean | 可临时停用而不删除 |

### 动作类型（14 种）

| type | 中文 | 目标 | 主要参数 |
|---|---|---|---|
| `character.show` | 角色出现 | 角色 | `side`: `fade` / `left` / `right` / `none` |
| `character.hide` | 角色离场 | 角色 | `mode`: `fade` / `out` |
| `character.move` | 角色移动 | 角色 | `x` / `y`（舞台百分比，-200–200） |
| `character.scale` | 角色缩放 | 角色 | `scale` 10–400% |
| `character.opacity` | 角色透明度 | 角色 | `opacity` 0–100% |
| `character.expression` | 切换表情 | 角色 | `expressionId` |
| `character.bob` | 上下浮动 | 角色 | `amplitude` 0.5–20 / `times` 1–6 |
| `background.change` | 背景切换 | 背景 | `assetId` / `transition`（6 种） |
| `camera.move` | 镜头平移 | 舞台 | `x` / `y`（-50–50） |
| `camera.zoom` | 镜头缩放 | 舞台 | `scale` 50–300% |
| `screen.fade` | 全屏渐暗/渐亮 | 舞台 | `to` 0–100 / `color` |
| `screen.flash` | 屏幕闪白 | 舞台 | `color` |
| `screen.shake` | 屏幕震动 | 舞台 | `strength` 0.5–6 |
| `wait` | 等待 | 舞台 | 无 |

**没有「执行脚本」这一类动作**，也没有 `eval` / `new Function` / 内联 JS 字符串字段。
作者能表达的只有上表 14 种声明式动作，工程文件里不可能夹带可执行代码——这既是安全边界，
也是「换机器、换版本仍能重放」的前提：动作表是纯数据，重放是纯函数。

### 为什么不直接存绝对时间

`mode` 表达的是**与上一动作的关系**，不是绝对时间轴：

- `after`：从「上一动作的结束」开始；
- `parallel`：从「上一动作的开始」开始（同一批并行动作共享同一个起点）。

这样作者拖动列表顺序就能改变语义，不用手算每一秒。时间轴由 `schedule()` 一次算出：

```js
let cursor = 0, lastStart = 0;
for (const a of list) {
  const start = (a.mode === 'parallel' ? lastStart : cursor) + (a.delay || 0);
  const end = start + (a.duration || 0);
  out.push({ action: a, start, end, blocking: a.blocking === true });
  lastStart = start;
  cursor = Math.max(cursor, end);
}
```

`totalDuration()` 取所有 `end` 的最大值（并行动作可能比前一个更早结束，不能取最后一项）；
`blockUntil()` 取所有**阻塞**动作 `end` 的最大值——它只有一个用途：**剧情推进要等到什么时候**。

## 3. 运行时：三个不可让步的性质

### 3.1 纯函数求值

```js
stateAt(before, actions, t, ctx) -> state
```

给定「进入本句前的状态」「动作表」「时间 t」，返回唯一确定的状态。没有隐藏累积、没有间接状态：

```js
state = { layers: { [layerId]: { dx, dy, scale, opacity, visible, assetId } },
          camera: { x, y, scale },
          screen: { dim, color, flash, flashColor, shakeX, shakeY } }
```

**`t = Infinity` 就是终态**。于是「跳过动画」= 用 `Infinity` 求值，天然与「正常播完」是同一个结果——
不是「尽量对齐」，而是同一个函数、同一份输入，代码里没有第二条路径。

顺带得到两个性质：

- `stateAt(stateAt(s, acts, 0.4), acts, Infinity)` 与 `stateAt(s, acts, Infinity)` 完全相同（中途结算 = 播完）；
- 终态再结算一次仍是终态（幂等），所以「重复执行 100 次」不会漂移到别的位置。

### 3.2 单一时间源

整段演出只有一个 `requestAnimationFrame` 循环。每帧用真实时间 `t` 求一次状态、写一次 DOM。
不为每个动作开 `setTimeout`，因此：

- 动作再多，定时器数量恒为 1；
- 换句、退出试玩、关闭预览只需要 `cancel()` 一次；
- 不存在「旧句子的定时器还在跑，把新句子的角色又挪走」这种事故——
  旧控制器在 `draw()` 开头就被取消，新句子从 `perfState`（已记账的终态）重新起步。

`prefers-reduced-motion: reduce` 或「不要动画」的场景直接取 `t = Infinity`，不启动循环。

### 3.3 状态外置，靠重放恢复

运行状态**不写进工程、不写进 DOM 属性**，只在内存里按 `layerId` 记账。

- 存档只存 `{id, trail}`（V0.6.1 就是如此，V0.8.0 没有改动存档格式）；
- 读档 / 后退 / 跳章 / 重新开始时，沿 `trail` 把每一句的演出**重放**一遍：

```js
st = emptyState();
for (const nodeId of trail) st = commit(st, actionsOf(nodeId), { P, layers: stageAt(nodeId) });
```

因为求值是纯函数，「一句一句点过来」和「读档后一步到位」得到的是同一份状态。
演出不需要序列化，也不存在「存档里存了一份过期的舞台状态」的可能。

## 4. 语义目标与「换立绘、换章节还指得对」

动作里存的是 `char:<characterId>` / `bg`，不是图层 ID。运行时按当前舞台图层表解析：

```js
resolveTarget(layers, type, 'char:lin_you')  // → 'c_lin_you'（当前这句里林悠的图层）
resolveTarget(layers, 'background.change', 'bg')  // → 这一句的背景图层
```

好处是：同一个「林悠从左侧进入」的动作，在这一句指向林悠的夏装图层，在那一句指向居家图层；
换章节后图层 ID 全变，动作依然命中正确的对象。目标图层被删除时不会抛错，只记一个孤立状态，
单测里有这条回归（`target 图层被删除不应抛错`）。

## 5. DOM 分层：为什么演出不碰外层

每一句渲染出来的舞台是：

```
#layersCanvas
  └ .visual-layer[data-layer="c_lin_you"]      ← 布局：left/top/width/height/opacity
      └ .pf-frame                              ← 演出：translate/scale/opacity（内层）
          └ img
```

- `effects.js` 写外层 `.visual-layer` 的 `transform` / `filter` / `left` / `top`；
- `performance.js` 写内层 `.pf-frame` 的 `transform` / `opacity`。

两层各自持有自己的变换，浏览器负责合成。这样 V0.7 的效果不会因为演出的位移被覆盖，
演出也不会把作者在布局里拖好的位置改掉（终态位移是 `translate(0,0)` 之外相对布局的偏移量，
`character.show` 结束后一律回到 0）。

舞台级的东西（镜头、震动、渐暗、闪白）挂在 `#layersCanvas` 与它的父容器上：

- 镜头 + 震动：`container.style.transform`（只作用于舞台）；
- 渐暗 / 闪白：`#stage` / `#scene` 下的 `.pf-overlay`（`pointer-events: none`，不挡点击）；
- 转场：`.pf-bg-ghost`（旧图 / 新图的合成层）。

播放器里 `#box`（对话框）是 `z-index: 5`，覆盖层是 3，所以「全屏渐暗」不会盖住台词。
真实窗口验收里有一条专门的断言：渐暗到 100% 后，对话框仍然在最上层、文字仍可见可读。

## 6. 背景转场

| transition | 过程 | 终态 |
|---|---|---|
| `cut` | 直接换图 | 新图 |
| `crossfade` | 新图以 ghost 层从 0 → 1 叠加，旧图在下 | 新图 |
| `fadeBlack` / `fadeWhite` | 先压到全黑/全白（0 → 1 → 0），过半时换图 | 新图 |
| `slideLeft` / `slideRight` | 新图从一侧滑入 | 新图 |

关键约束是 M2 要求的「切换前必须预加载，避免空白帧」：目标素材在动作开始前就已经在工程里
（同源 data URI 或 `paper://` 受控协议，无需网络），ghost 层用 `background-image` 引用同一份数据，
不会出现「先白一下再出图」。真实窗口验收记录了 `crossfade` 中途的 ghost 透明度
（0.396，既不是 0 也不是 1），证明它是真的在过渡，而不是瞬间换图。

## 7. 持久化、迁移与导出

- **schema 6**：`toV6()` 给每个节点补 `performance: null`，迁移链 `1→2→3→4→5→6` 全部接上；
  schema 5 的旧工程照常打开，`performance === null` 时运行时走「没有演出」分支。
- **校验**：`core.validate()` 里 `schema >= 6` 时调用 `checkPerformance()`：动作 ID 唯一、
  类型在表内、目标字符串、时长/延迟 0–30、缓动与 mode 白名单、参数逐项范围、单节点上限 200 条。
  非法参数在入口就抛错，不会流进 CSS（单测覆盖 `NaN`、字符串数字、越界值）。
- **导出**：`referencedImageIds()` 把演出里 `background.change` 用到的 `assetId` 也算进引用，
  否则目录版 / 单文件导出会漏掉「只在演出里出现」的背景图，运行时表现为空白。
- **导出体积**：演出动作是纯 JSON（一条约 150 字节），54 条动作不到 10 KB，
  对 30 MB 的单文件试玩版没有可测量的影响。

## 8. 为音频演出与多轨时间轴预留的位置

本轮**不实现**多轨时间轴与音频演出，但数据模型留了扩展位：

- `version` 字段：未来加「音频轨道」「关键帧」时可以升到 2，旧动作仍然可读；
- 每种动作只有「目标 + 参数 + 时间关系」，加 `audio.play` / `audio.fade` 不需要改调度器，
  只需要在 `applyStep` 里多一个分支（音频是副作用，不进入 `state`）；
- `mode` 的 `after` / `parallel` 语义可以自然扩展出「相对某个动作」的锚点。

换言之：调度、求值、终态一致性、录制与重放这些地基不会被下一轮推翻。

## 9. 性能设计

- 单 rAF、每帧一次 `stateAt`；动作数在 200 以内时，求值成本是「动作数 × 常数」的线性扫描，
  实测 54 条动作的整段演出在真实窗口里保持满帧（见 `release/performance-benchmark.json`）。
- 每帧不重建 DOM：只改 `transform` / `opacity` / `img.src`，并且 `img.src` 只在变化的帧写一次。
- 终态清理：不可见图层的透明度归一、`flash` / `shake` 归零、`dxEntry/dyEntry` 清除，
  避免「演完还在轻微抖」或「下次出现从半透明开始」。
- 与 V0.7.6 的流式素材体系不冲突：演出只引用 `assetId`，实际 URL 由既有解析逻辑提供
  （`paper://` / `pvres://` / `papergame://` / `data:`），不额外复制字节。

## 10. 已知边界

- 没有多轨时间轴：并行只能表达「与上一动作同时开始」，不能拖动到任意时刻。
- 没有音频演出：BGM 仍由 V0.5 的音频运行层按节点切换。
- 没有 Live2D / 骨骼 / 粒子：角色只有整图位移、缩放、透明度、表情换图、上下浮动。
- 镜头只作用于舞台：这是刻意的——对话框和 UI 不跟着抖，才不会影响阅读。
